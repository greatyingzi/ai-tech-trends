先弄清楚：PTC 是什么

DSH（DeepSeek Harness）里有两种让 AI 使用工具的方式。普通模式下，模型每次只能点名调用一个工具，比如"读这个文件"，然后等结果回来，再决定下一步。

PTC（程序化工具调用）模式不一样：模型提交一段程序（叫做 run_code），在这段程序里可以连续调用多个工具，甚至同时发起好几个互不依赖的调用。可以把它理解为——普通模式是"每次跑一趟腿"，PTC 是"给 agent 一张清单，让它一次在后台办完"。

PTC 下的工具不是直接点名叫的，而是由 DSH 自动生成一套工具说明（SDK 声明）放进系统提示里，模型照着这套说明在程序内调用。当前环境默认是"一次性进程"：每段程序运行完就结束，不保留上次程序里的变量。

问题出在哪：默认用法又慢又贵

我们统计了 224 个真实会话、32,735 段程序，发现模型虽然"会用" PTC，但用得很退化：

  • 只有 2.4% 的程序做过批量调用；67% 的程序里只调用了一个工具。
  • 有 887 段程序在循环里一个一个地 await 工具，而这些调用彼此并没有依赖关系。
  • 还有大量"同一轮对话里连续提交多个程序"的情况，等于每次都重新启动一遍。

为什么会这样

不是模型不会并发，而是环境没有把它变成默认习惯：提示词里只写了"独立调用可以（MAY）重叠执行"——这是许可，不是要求。任务描述只要带一句"按顺序逐项检查"，模型就会老老实实串行。

更关键的是成本结构。模型每次新调用都要把它已经知道的内容重新送一遍，这部分叫"缓存命中（cache read）"。在实际统计里，它占 token 总量的 85% 以上，是账单的大头。所以少一次模型调用，不只是少等一轮，更是少重读一遍完整上下文。

怎么解决的：把并行写成默认行为

我们没有改 DSH 插件源码、没有改配置、没有重启服务。只用了 DSH 自带的一个机制：dsh-agent-instructions 会在每个会话的第一次请求时，自动加载你的全局指令文件 ~/.agents/AGENTS.md。这个文件本来就会进入上下文，所以往里加规则的边际成本几乎为零，而且每个会话都会生效。

曾经考虑过写 skill（技能文件），但 skill 只有模型"想起来读"的时候才会命中，命中率不确定，读它本身也要花 token——不适合承载"默认行为"。

加入的 7 条规则

## PTC 脚本默认行为（全局，所有会话）

1. 一个任务尽量一个 run_code；相位之间用 await 在同一程序内衔接，
   不要拆成多次 run_code。
2. 写程序前先列依赖图：无数据依赖的调用全部放进同一个
   Promise.allSettled([...])；只有真依赖才串行 await。
3. 禁止 for (...) await tools.x(...)；改成
   await Promise.allSettled(items.map(x => tools.x(...)))。
4. 任务措辞即使写着"按顺序/逐项"，只要无数据依赖仍批量执行。
5. 可并发的 safe 工具：read / read_image / web_fetch / web_search /
   session_trace / session_event_trace / session_event_read /
   subagent / list_agents。bash / grep / glob / edit / write 在底层
   本来就是串行的，但仍应放进同一程序以省往返。
6. return 只给摘要，中间结果留在程序局部，不往对话里堆。
7. bash 里 node 不在 PATH，用 /opt/homebrew/bin/node 或
   await import("node:...")，别先试 which node。

我该怎么用

第 1 步 打开（或新建）~/.agents/AGENTS.md。
第 2 步 把上面那段 ## PTC 脚本默认行为 连同 7 条规则复制进去，放在文件末尾。
第 3 步 开一个新会话即可生效；当前会话通常也会收到文件变更提醒，但干净的做法是新开会话。
第 4 步（可选验证） 给 agent 一个明显能并行的任务，例如"分别读取 6 个配置文件并统计某个字段"。看它是否写了一个包含 Promise.allSettled 的程序，而不是分 6 次调用。
后悔了怎么办 把这段从文件里删掉，下个会话就恢复原样；没有任何服务需要重启。

注意：这条规则是写给 PTC 模式用的。如果你的会话不是 PTC 预设，工具调用形态不同，效果也会不同。

效果：两个目标都达成

对照测试（同一任务、同一模型，改规则前后各跑一遍）

任务模型调用次数总 token（含缓存）节省耗时
统计多个配置文件6 → 2143,849 → 46,964−96,885（−67%）37s → 28s
混合统计任务10 → 4278,086 → 99,941−178,145（−64%）57s → 30s
另一组同类任务6 → 2201,965 → 46,964−155,001（−77%）37s → 28s

这三组任务的答案都正确（9/9），也就是说速度提升没有以答案为代价。

真实使用一天后的变化

  • 做过批量调用的程序占比：2.16% → 34.20%（约 16 倍）；批量调用涉及的调用数占比：4.92% → 58.86%（约 12 倍）。
  • 出现真正并行重叠的程序：1.28% → 24.54%（约 19 倍）。
  • 每轮对话需要的程序数和步骤数都约减半。

按实际会话反推：改规则后一天内有 97 个批处理程序，省下 275 次模型调用。这些程序实际花了约 826 万 token；如果还是老办法、每个工具调用各占一次模型请求，需要额外约 2,150 万 token，其中 1,837 万是缓存重读——这正是账单大头。（若按缓存单价折扣折算，账单等价约 500 万 token，但按 token 总量就是 2,150 万。）

质量有没有下降

没有看到系统性退化：重复调用占比 6.18% → 4.64%；结果错误占比 3.76% → 2.02%；轮次失败率 10.95% → 8.57%。有两类情况值得留意：

  • 混合型任务里，模型有时仍会绕开工具、直接在程序里用 Node 读写文件。这样做更快，但工具日志看不到这些操作，属于观测与治理问题。
  • 单个程序塞进去的逻辑变多后，程序本身的语法错误会让整批调用一起失败。目前只在个别会话出现，还在观察。

另外，长篇代码编辑类任务本来就是一步步改文件，天然没什么可并行的；这类任务批处理率低是正常的，不算退步。

常见问题

需要改 DSH 或重装什么吗？

不需要。只改一份会自动加载的文本文件，不改插件、不改配置、不用重启。

每个会话都会生效吗？

会。dsh-agent-instructions 在会话首次请求时加载 ~/.agents/AGENTS.md，属于用户全局指令链；子 agent 也会加载。

为什么不写成 skill？

skill 需要模型主动去读，命中不稳定，而且读 skill 本身要花 token。这条规则要的是"默认行为"，必须放在每次必加载的指令里。

我用的是非 PTC 模式，有用吗？

意义不大。这套优化针对的是 PTC 里"一个工具调用 = 一次模型请求"的退化用法。

数字是怎么来的？

两部分：一是改规则前后同一任务各跑一遍的对照实验；二是改规则前后真实会话日志的统计（token 数据取自每次模型调用记录的实际用量）。反事实部分明确标注为估算，不当作实测。

本文所有数字均来自实测或明确标注的估算。规则文件位置：~/.agents/AGENTS.md。
