什么是 PTC

PTC（Programmatic Tool Calling，程序化工具调用）是 DSH 的一种工具执行模式：模型不再逐个点名调用工具，而是提交一段程序（run_code），由程序在运行时通过生成的 SDK 调用其他工具。

实现由 @deepseek-ai/dsh-tool-executor-ptc 提供，向系统提示注入三部分：

  1. tools:ptc-only 规则：唯一可直接调用的工具是 run_code，其他工具必须从程序内部调用；直接点名调用会被判 UNKNOWN_TOOL。
  2. tools:sdk 段：自动生成的 TypeScript 声明——可见工具按字典序排列，description 变成 JSDoc，JSON Schema 转成 TS 类型。原生工具 schema 被省略，这段 SDK 是模型获知工具参数与用途的唯一来源。
  3. run_code schema：code（async 函数体）与 description 必填；可选 timeoutMs（默认 120s、上限 600s）、sandbox_permissions + justification。

关键特点

  • code 是 async 函数体而非完整文件；顶层 await/return 可用；只接受可擦除 TypeScript（禁 enum/namespace）。
  • 工具经 await tools.name(args) 调用；失败抛 ToolCallError；只有 console.log 和 return 的值成为输出。
  • 执行管线按 isConcurrencySafe(args) 把工具分为并发安全与 exclusive barrier 两类。当前 safe 工具仅 9 个：read、read_image、web_fetch、web_search、三个 session 查询工具、subagent、list_agents；bash/grep/glob/edit/write 均为 exclusive。
  • 本环境为 per-call 模式：每次 run_code 都是全新 Node 进程，不保留跨调用状态（已实测）。

典型漏并行

// 5 张独立图片逐个等待（此类程序 887 个）
for (const s of ["qa_dense_01", "qa_dense_02", "qa_dense_03"]) {
  await tools.read_image({ file_path: \`.../\${s}.png\` });
}

根因

  1. SDK 指令只说 "Independent read-only calls MAY overlap under Promise.all"——许可，不是要求。
  2. 任务措辞能压倒能力：改成"按清单顺序逐项核对"，批处理率从 54.5% 掉到 0%，还多读一遍。
  3. 生成的 SDK 没有并发安全标注，模型不知道该批谁。
  4. exclusive 工具一出现，扇出就消失；模型转而发现 direct-fs 逃逸。

优化方案：怎么做的

候选判定
写 skill否决：不自动注入、命中靠运气、读 skill 本身费 token
改全局 systemPrompt.personaPrefix否决：无通用自由文本字段，且被 ptc preset 的 persona 在 agent scope 覆盖
改 PTC_ONLY_INSTRUCTION 源码效果精准但需改插件并重载，成本高；暂不上
写进 ~/.agents/AGENTS.md采用：dsh-agent-instructions 在会话首请求必加载用户全局指令链；文件已注入，边际成本近零

落地的 7 条规则

  1. 一个任务尽量一个 run_code；相位间用 await 在同一程序内衔接。
  2. 写程序前先列依赖图：无数据依赖的调用全部放进同一个 Promise.allSettled([...])。
  3. 禁止 for (...) await tools.x(...)，改成 items.map(...) 放进 allSettled。
  4. 任务措辞即使写着"按顺序/逐项"，只要无数据依赖仍批量执行。
  5. 标明可并发的 safe 工具；exclusive 工具仍应放进同一程序省往返。
  6. return 只给摘要，中间结果留在程序局部。
  7. bash 里 node 不在 PATH，用 /opt/homebrew/bin/node 或 await import("node:...")。

影响面与回滚：所有会话（含子 agent）每次首请求多约 500 字节指令；不改插件、不改配置、不需重启。删除该 section 即可回滚。

真实会话的反事实总账

改规则后真实会话里有 97 个批处理程序、372 次嵌套调用，等价省下 275 次模型调用。这批程序实际消耗 8,269,196 token；若不批量、改成 275 个独立模型步，按每步重送实测上下文计算，需额外 21,533,385 – 21,928,137 token（缓存重读占 85%），总账约 2.6 倍。

拆开 21.5M：新输入 2,853,792、缓存重读 18,374,656、输出 304,937。按 token 总量口径就是省约 2,150 万；若按 cache=0.1× 输入价折算账单等价约 500 万。

质量、边界与后续

质量未退化：干净房间 9/9 正确；重复调用占比 6.18% → 4.64%；result 错误/dispatch 3.76% → 2.02%；turn 失败率 10.95% → 8.57%。dispatch 错误率 1.64% → 6.05% 上升，抽查后主要是可恢复的过程性失败（文件不存在、edit 锚点不匹配、编译被 abort）。

三个残留问题：

  • 混合任务仍会逃逸 direct-fs（7.38% → 9.66%），工具日志看不到 I/O——属于插件层治理。
  • 长序列代码编辑任务有时忽略批处理规则（复盘会话中一个 0 处漏批、一个 12 处漏批）。
  • 单程序塞更多逻辑，语法错误会让整批调用一起失败——目前仅单会话样本，需继续观察。

后续可做的插件层优化：给 grep/glob 标 isConcurrencySafe、在生成的 SDK 里标注并发安全、排查 885 个"源码有工具调用但无 dispatch 事件"的日志缺口、决定是否允许 direct-fs。

结论

只改了一份每会话必注入的文本文件，就同时达成两个终极目标：总 token 下降（省钱）与并行减少调用（省时）。关键不是让模型"更努力地并发"，而是把批处理写成默认行为——提示词里一句 "MAY overlap" 不够，必须写成硬规则。
